## 3. Manual order placement — service

- [x] 3.1 Widen `ICheckoutActor` in `order.interface.ts` with `{ kind: "staff"; staffUserId: string }` and extend its doc comment to cover the third case. Compile and list every `actor.kind` branch the compiler now rejects.

- [x] 3.3 Handle the `staff` case in `resolveCheckoutContext`: resolve the customer through `CustomerService.getOrCreateCustomerByPhone`, create the address through `createInlineShippingAddress`, skip `enforceGuestOrderLimits` and skip the `checkoutConfig` field map and `allowGuestCheckout` gate. Keep the phone floor and require `addressLine1`.
- [x] 3.4 Handle the `staff` case in `quoteCheckout`, which also takes an `ICheckoutActor`. A staff quote prices the payload's lines and resolves no cart and no customer — today the `user` branch runs `getOrCreateCustomerByUserId`, which would silently turn the operator's own account into a customer. Accept an optional `discountAmount` on the quote payload for this actor only, and pass it to `quoteCharges` where the coupon discount goes, so the quoted tax reflects the discounted line amounts. The admin's manual order form depends on this (admin design.md, Decision 2) — it is not optional.
  **Deviation from the plan:** the design assumed `POST /orders/quote` would learn the staff actor. It cannot decide the actor by role: that route runs under `optionalAuth`, and an ADMIN shopping on the storefront is a shopper like any other whose own cart must still price. Building a staff actor from the session's role would break that. Added `POST /orders/quote/manual` under `checkAuth(...ADMIN_PANEL_ROLES)` instead — the actor is staff because the ROUTE is staff, which is a property of the endpoint rather than a guess about the person, and it keeps `discountAmount` unspellable on the shopper's quote. Same reasoning as design.md Decision 2's two-routes argument for placement.
- [x] 3.5 Thread the staff discount into `placeOrder`: `discountAmount` reaches `quoteCharges` where the coupon discount does today, and `discountReason` is written to the order. Reject a discount exceeding the subtotal — after pricing, since the subtotal is not known before the lines are read.
- [x] 3.6 Set the new order fields for a staff actor: `channel` from the payload, `createdByUserId` from `actor.staffUserId`, `isGuestOrder: false`, `guestIp: null`, and `statusHistory.create.changedById` to the staff user. Confirm the starting status stays `PENDING`.
- [x] 3.7 Widen the COD `Payment` creation condition from `isGuest` to `isGuest || actor.kind === "staff"`, and update its comment to say the condition is "this order is cash-on-delivery", not "this actor is a guest" (design.md, Decision 7). Leave the authenticated storefront path's behaviour unchanged.
- [x] 3.8 Add `placeManualOrder` — the thin wrapper that turns `IManualOrderPayload` into `placeOrder`'s payload and actor, mirroring `placeLandingPageOrder`'s shape and its doc comment, including the table of what does and does not differ from a checkout (design.md, Decision 3).
- [x] 3.9 Confirm no second implementation crept in: order number generation and retry, `loadPayloadLines`, `quoteCharges`, `deductStockForOrderLines`, idempotency replay, and both notifications must all still be reached through the shared core. **Audited:** exactly one `order.create(` in the module (line 1101, inside `runCheckout`); `generateOrderNumber` 1 call site; `loadPayloadLines` and `quoteCharges` 2 each (placeOrder + quoteCheckout, both pre-existing); `deductStockForOrderLines` 2 (placeOrder and the pre-existing `ensureDeliveredOrderStockDeducted` reconciliation, not a creation path); `findReplayableOrder` 2 (replay check + race winner); both notifications 1 each. `placeManualOrder`'s body is a payload mapping and a single `placeOrder` call — no branching, no queries.
