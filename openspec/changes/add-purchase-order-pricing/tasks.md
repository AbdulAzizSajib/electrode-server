## 3. Staging on create and amend

Add a comment stating the above-cost rule is deliberately NOT enforced here — it depends on the landed cost the receipt computes from header shipping/tax and every other line, so it is a transactional service invariant, and the specified answer is to warn rather than refuse (design.md Decision 6). Verify a negative and a three-decimal value are rejected, and that a payload with both fields absent still passes. **Done — 8 cases verified** (both absent, both set, one set, zero allowed, negative rejected on each, and the same through `amendPurchaseOrderZodSchema`, which extends the shared line schema so one edit covered both). **Deviation from this task's own wording, deliberate:** three decimals are NOT rejected. ## 4. Reporting the item's current prices on a line

- [x] 4.1 In `purchase-order.service.ts`, extend the line's product/variant include so a read reports the item's current `purchasePrice`, `offerPrice` and `sellingPrice`, with **variant-then-parent precedence for each** — the same precedence `receivePurchaseOrder` already uses when it values the line. Add a comment that these are read at request time, are never snapshotted onto the line, and never alter `unitCost`/`totalCost`/any total. **Done via `resolveItemPrices` + `withItemPrices`, attached as a derived `itemPrices` per line.** Precedence is resolved FIELD BY FIELD, not whole-row: a variant may override the offer price and inherit the regular one, so picking "variant else product" for all three at once would report nulls for the ones it does not set. Wired into the detail read and the create response but deliberately NOT the list read — the list renders one row per order and never shows a line's prices, so resolving them there would be work nothing reads (the list also casts its rows to `{id, totalAmount}`, which erases `items` from the type).

Then change a product's `offerPrice` and verify the same line reports the new figure while its `unitCost` and `totalCost` are unchanged. **All verified against a real fixture (7 checks):** simple product reports its own three; a variant that prices itself reports 200 not the parent's 150, and falls back to the parent's 175 for the regular price it does not set; its cost basis takes precedence too; a variant with no prices inherits all three; and after changing the product to 199 the line reports 199 while `unitCost` 95 / `totalCost` 475 are untouched.
