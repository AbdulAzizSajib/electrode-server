## Context

See proposal.md for motivation. What shapes this design is that the current write path was built on the assumption that images and variants are independent sibling collections, and that assumption is load-bearing in three places:

- **`createProduct` is one flat nested `create`** (`product.service.ts`) — product, variants, images and attributes are written in a single Prisma statement with no transaction. Nothing inside that statement can reference an id generated by it, so an image cannot point at a variant created in the same call.
- **`updateProduct`'s `$transaction` runs `syncProductVariants` before `syncProductImages`.** That order is currently arbitrary; once images reference variants it stops being arbitrary, and the current order happens to be the correct one — variants must exist before images name them.
- **The three `sync*` helpers all reconcile by "delete what the payload omits."** `syncProductVariants` deleting a variant would, under a cascading FK, take that variant's images with it. `syncProductImages` deleting an image is already the established contract and stays.

Two further constraints come from outside the service:

- **`validateRequest` zod-strips unknown fields** before the controller runs, so any new payload field silently vanishes unless it is declared in `product.validation.ts`.
- **`imageSlots[i]` is positional-only** — it describes the `i`-th uploaded file and carries no stable key. It is the only metadata channel an uploaded file has, so it is where an uploaded file's variant reference has to travel.

`PUBLIC_PRODUCT_DETAIL_SELECT` is an explicit allowlist (it exists to keep `costPrice` out of public responses), so a new field reaches the storefront only if added there deliberately.

## Goals / Non-Goals

**Goals:**
- One request creates a product, its variants, and images already associated with those variants — no create-then-update round trip from the admin client.
- The same association mechanism works for URL-based images and uploaded files, and on both create and update.
- An invalid variant reference fails the whole request rather than being silently dropped or silently stored.
- Existing rows, existing payloads, and existing response consumers keep working untouched.

**Non-Goals:**
- Not making `ProductVariant.image` and `ProductImage.variantId` a single source of truth in this change. `image` is kept and derived; retiring it is a separate change once the cart and wishlist read paths move.
- No many-to-many image sharing between variants (see Decision 2).
- Not solving the orphaned-Cloudinary-upload gap that `add-product-image-upload` Decision 5 accepted. This change inherits it unchanged.
- No reordering or re-sorting semantics beyond the existing `sortOrder` — this change decides *which* images belong to a variant, not how they are ordered within it.

## Decisions

**1. The FK lives on `ProductImage` as a nullable `variantId`, not on `ProductVariant` as an `imageId`.** A variant needs several images (front, back, in-case) and an image depicts at most one variant, so the many side is the image. Nullable is what carries the semantics the proposal needs: `null` is not "unassigned, fix later" but a meaningful state — *shared by every variant* — which is what a charging-case or size-chart photo genuinely is. It is also what makes the migration additive: every existing row is already correct as a shared image, so nothing needs backfilling and no product's appearance changes on deploy.
- *Alternative considered*: `ProductVariant.imageId` pointing at one `ProductImage`. Rejected — it is `ProductVariant.image` again with an FK, and caps a variant at one photo, which is the limitation this change exists to remove.
- *Alternative considered*: keep using `ProductVariant.image` and have the storefront match by URL string. Rejected — string-matching a variant to a gallery slot breaks the moment the same asset is uploaded twice under different Cloudinary URLs, and it cannot express a variant having more than one image.

**2. `onDelete: SetNull`, and `syncProductVariants` must not cascade-delete images.** Deleting a variant is a routine catalog edit — renaming an option, restructuring a product's variant set. Photography is expensive and the admin who removes a variant is not asking to destroy its photos. Under `SetNull` those images become shared, which is visible and recoverable; under `Cascade` they are gone and the only remedy is re-uploading. The corresponding spec scenario ("Removing a variant preserves its images") is the observable contract; `SetNull` is how the database enforces it even for deletes that do not go through `syncProductVariants`.
- *Note*: this is deliberately the opposite choice from `ProductImage.productId`, which is `Cascade` — deleting a *product* should take its images, because nothing is left for them to belong to.

**3. Create resolves variants by position (`variantIndex`); update resolves them by id (`variantId`); both fields are accepted on both endpoints.** On create there are no variant ids to reference, so an image names its variant by index into the request's own `variants` array — the client already controls both arrays in one request, which is the same reasoning `add-product-image-upload` Decision 1 used to justify positional `imageSlots`, applied to the same problem one level up. On update, existing variants have real ids and using them is unambiguous. Update must still accept `variantIndex` because a single update can add a new variant *and* an image for it. Accepting both fields on both endpoints avoids a create/update asymmetry in the client and in the validation schema; when both are present on one image, `variantId` wins and `variantIndex` is ignored.
- *Alternative considered*: client-generated temporary ids (`"tmp-1"`) for new variants, referenced by images and swapped server-side. Rejected — a second identifier namespace to validate and collision-check, for no expressiveness the array index does not already provide.
- *Alternative considered*: create-then-PATCH, letting the admin client do a second request once ids exist. Rejected — a partially-correct product is briefly visible, and a failed second request leaves it that way.

**4. `createProduct` becomes a `$transaction`, matching `updateProduct`'s existing shape.** Resolving `variantIndex` requires the generated variant ids, so the write splits into product + variants + attributes first, then images with resolved `variantId`s. That is two statements where there was one, and a failure between them would otherwise leave a product with variants and no images. `updateProduct` already establishes `$transaction` as this module's pattern for multi-statement writes, so this is applying the existing convention rather than introducing one.

**5. Variant references are validated before the transaction opens, alongside the existing precondition checks.** `assertCategoryExists`, `assertBrandExists`, `ensureUniqueProductSku` and `ensureUniqueVariantSkus` already run outside the transaction and throw `AppError(400)`. Variant-reference validation joins them: an out-of-range `variantIndex`, or a `variantId` not belonging to this product, throws there. This keeps the "reject with 400, nothing modified" spec scenario true by construction — the request fails before any write — and it keeps the cross-product-leak check (a `variantId` from someone else's product) in the same place as the other ownership checks rather than buried in a sync helper.

**6. `updateProduct` keeps variants-before-images ordering, and image sync resolves `variantIndex` against the post-sync variant set.** The existing order is already correct for this change; what it needs is for `syncProductVariants` to hand back the index-to-id mapping for the variants it created, so `syncProductImages` can resolve a `variantIndex` naming a variant that did not exist when the request was received. Ordering is now a correctness constraint rather than an incidental one and should be commented as such, since a future reordering would break it silently.

**7. `ProductVariant.image` is derived, not authored.** After images are synced, each variant's `image` is set to the `url` of its lowest-`sortOrder` linked image (and to `null` when it has none). This keeps `cart.service.ts` and `wishlist.service.ts` — which read `variant.image` and are not touched by this change — showing the same photo the product page shows, instead of two independently-authored fields drifting apart. An `image` value supplied directly in a variant payload is still honored when that variant has no linked images, so existing clients that set it keep working.
- *Alternative considered*: leave `image` entirely alone. Rejected — the cart would keep showing a stale or empty variant photo while the product page shows the linked one, which reads as a bug to the shopper and is exactly the kind of divergence a derived field prevents.

**8. `variantId` is projected into both the public detail and admin detail responses; list projections are left alone.** `PUBLIC_PRODUCT_DETAIL_SELECT.images` and `PRODUCT_DETAIL_INCLUDE.images` gain the field. The list projections (`PUBLIC_PRODUCT_LIST_SELECT`, `PRODUCT_LIST_INCLUDE`) take only the primary image and render one thumbnail per card — they have no variant selector, so the field would be dead weight on every listing row. `searchProducts`' raw-SQL image subquery is likewise untouched.

## Risks / Trade-offs

- **[Risk]** The primary image (`isPrimary`) may belong to a variant, so a product card thumbnail could show the navy variant while the card's price is the default product price → **Mitigation**: none needed in this change — `isPrimary` and `variantId` are independent, and an admin choosing a variant photo as the primary is a deliberate merchandising choice, not an error. Worth stating in the admin UI copy so it is not a surprise.
- **[Risk]** A variant with no images of its own shows a gallery of only the shared images, which may be empty if the admin assigned *every* image to a variant → **Mitigation**: a storefront-side concern (its change specifies falling back to the full image set rather than rendering an empty gallery); server-side, nothing prevents or requires shared images.
- **[Risk]** Deriving `ProductVariant.image` (Decision 7) overwrites a value an existing client set directly, if that variant also has linked images → **Mitigation**: derivation only applies when the variant has at least one linked image, so a client that sets `image` and links nothing is unaffected; the case where both are supplied is precisely the one where they would otherwise disagree.
- **[Risk]** `createProduct` moving to a transaction lengthens the write and adds a failure mode (transaction timeout) where there was one statement → **Mitigation**: the same two-phase shape `updateProduct` already runs in production for the identical data volume; no new query patterns, no N+1 introduced.
- **[Risk]** `variantIndex` couples an image to the *position* of a variant in the same request; a client that reorders `variants` between building `images` and submitting will mis-assign silently → **Mitigation**: validation catches out-of-range indices but cannot catch a wrong-but-valid one. This is the accepted cost of positional matching, consistent with `imageSlots`; the admin client is specified to build both arrays from one source of truth in the same pass.

## Migration Plan

1. **Schema** — add `variantId String?` + `variant ProductVariant? @relation(..., onDelete: SetNull)` + `@@index([variantId])` to `ProductImage`; add the `images ProductImage[]` back-relation to `ProductVariant`. Hand-named timestamp migration folder with a header comment citing this change and Decision 2, matching the convention of `20260831083400_add_campaign_placement`.
2. **Contract** — add `variantId?` / `variantIndex?` to `IProductImageInput` and `IImageSlotInput` and to their zod schemas, so `validateRequest` stops stripping them.
3. **Controller** — `mergeUploadedImages` copies the two new fields from `imageSlots[i]` onto the image input it builds. No other controller change.
4. **Service** — `createProduct` → transaction with variant-id resolution; `updateProduct` → thread the new-variant index map from `syncProductVariants` into `syncProductImages`; `syncProductVariants` → null out `variantId` on images of removed variants instead of relying on cascade; add variant-reference precondition checks; derive `ProductVariant.image`; extend the two detail projections.
5. **Backfill (optional, separate SQL)** — set `ProductImage.variantId` where `ProductVariant.image` equals the image's `url` within the same product. Not required for correctness; it converts existing single-variant photos into the new model so those products benefit without an admin re-editing them.

**Rollback**: the column is nullable and additive, and every read path treats `null` as "shared". Reverting the application code while leaving the column in place is safe — the field simply stops being written or projected, and the storefront falls back to the flat gallery. Dropping the column requires reverting the application code first.
