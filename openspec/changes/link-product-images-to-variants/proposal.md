## Why

A product's images and its variants are stored with no relation between them. `ProductImage` carries only `productId`, so for a product with a mint-green and a navy-blue earbud variant, the database knows there are four photos and two variants but not which photo shows which variant. The storefront therefore renders one flat gallery whose thumbnails are, from the shopper's point of view, in arbitrary order and unrelated to the option they are choosing — clicking the navy photo shows navy but keeps quoting the mint price.

`ProductVariant.image` exists as a single nullable URL string and is the closest thing to a link today, but it is a bare string outside the `ProductImage` table, it holds exactly one photo per variant, and nothing on the storefront reads it. It cannot express "these three photos are the navy variant" or "this photo of the charging case belongs to every variant".

## What Changes

- **`ProductImage` gains a nullable `variantId` foreign key.** A non-null `variantId` means the image depicts that specific variant; `null` means the image is shared by the whole product (charging case, box contents, size chart) and is shown regardless of which variant is selected. Nullable is what makes this additive: every existing row stays valid and shared, so no product changes appearance on deploy.
- **Product create accepts `variantIndex` on image inputs.** On create, variants have no ids yet — they are generated by the same request. An image may therefore reference its variant by position in the request's `variants` array, and the server resolves that position to the generated `ProductVariant.id`.
- **Product update accepts `variantId` on image inputs.** On update, existing variants have real ids, so images reference them directly. `variantIndex` remains accepted on update for images attached to variants being created in that same request.
- **Uploaded files can be assigned to a variant.** `imageSlots[i]`, which already describes the `i`-th uploaded file positionally, gains the same `variantId` / `variantIndex` fields, so a newly uploaded file lands on a variant in the request that uploads it.
- **A variant reference is validated against the product.** An image naming a `variantId` that belongs to a different product, or a `variantIndex` with no corresponding entry in `variants`, is rejected with 400 rather than silently stored or silently dropped.
- **Deleting a variant does not delete its images.** Images of a removed variant become shared (`variantId` set to null) rather than disappearing, so an admin removing a variant never silently destroys photography.
- **The public product detail response includes each image's `variantId`.** This is the field the storefront needs to filter the gallery and to map a thumbnail back to the variant it depicts.
- **`ProductVariant.image` is retained and kept in sync.** It is not dropped in this change: the cart drawer, wishlist and existing clients read it. It is derived from the variant's first linked image so the two never disagree, and is documented as superseded.

### Modified Capabilities
- `api/catalog`: Admin catalog management gains the ability to associate each product image with a specific variant (or leave it shared across variants), including on create where variant ids do not yet exist, and including for uploaded files. The public product detail requirement gains the guarantee that image-to-variant association is present in the response so a storefront can render a variant-aware gallery.

## Impact

**Schema (migration required)**
- `ProductImage` gains `variantId String?` with a relation to `ProductVariant` and an index. `onDelete: SetNull` — deleting a variant orphans its images to shared rather than cascading them away.
- `ProductVariant` gains an `images ProductImage[]` back-relation. No column is added or removed on `ProductVariant`; `image String?` stays.
- Additive and nullable throughout, so no backfill is required for existing rows. An optional one-time backfill can populate `ProductImage.variantId` where a `ProductVariant.image` URL matches an existing `ProductImage.url`.

**API**
- `POST /products` and `PATCH /products/:id`: `images[]` accepts `variantId` and `variantIndex`; `imageSlots[]` accepts the same two fields.
- `GET /products/:slug` (public detail) and `GET /products/admin/:id`: each image in `images[]` carries `variantId`.
- All additive — existing request payloads and existing response consumers are unaffected.

**Code**
- `prisma/schema/ProductImage.prisma`, `prisma/schema/ProductVariant.prisma`, plus a new migration.
- `product.interface.ts`, `product.validation.ts`: new optional fields on the image, variant-image-slot and update payload types.
- `product.service.ts`: `createProduct` becomes a transaction so variant ids exist before images are written; `updateProduct`'s transaction reorders to sync variants before images and resolves `variantIndex`; `syncProductVariants` stops hard-deleting images of removed variants; `PUBLIC_PRODUCT_DETAIL_SELECT` and `PRODUCT_DETAIL_INCLUDE` project the new field.
- `product.controller.ts`: `mergeUploadedImages` carries the two new slot fields onto the image inputs it builds.

**Consumers**
- Admin panel and storefront each need their own change to produce and consume the association; this change ships the contract they build against.
- `cart.service.ts` and `wishlist.service.ts` continue reading `ProductVariant.image` and are unaffected.

**Not in scope**
- No change to `POST /upload/image`.
- No removal of `ProductVariant.image`, and no migration of existing clients off it.
- No image-to-many-variants sharing: one image belongs to at most one variant, or to none.
