## 7. Follow-ups surfaced during implementation

- [x] 7.1 **`Banner.image` was NOT NULL while the spec says a DYNAMIC banner needs no artwork.** A `{type:"DYNAMIC", title:"..."}` create passed zod and then failed at the database — the exact validation/storage disagreement this change exists to remove. Surfaced to the user rather than decided unilaterally (it was outside task 1.3's enumerated column changes); the user chose to make the column nullable. Added migration `20260830050240_banner_image_nullable` (`ALTER COLUMN "image" DROP NOT NULL`) and set `image String?` in the schema. That migration also carries an intentional `ALTER COLUMN "placement" DROP DEFAULT`, generated from schema drift: the `'HEADER'` default from `20260830044311` existed only to backfill pre-existing rows and the model deliberately has no `@default`, so dropping it now that the backfill has run is correct. Both statements are documented in the migration file itself.
- [x] 7.2 **Bug found by task 6.7: every PATCH silently forced `type` to `IMAGE`.** `updateBannerZodSchema` was `z.object(bannerFields).partial()`, and `bannerFields.type` carried `.default("IMAGE")` — but zod's `.partial()` does **not** strip a default, so an omitted `type` parsed to `"IMAGE"` and overrode the stored `DYNAMIC` during the service-layer merge. Any update to a DYNAMIC banner that did not resend `type` was rejected as an invalid IMAGE banner. Fixed by moving the default onto `createBannerZodSchema` only, leaving `bannerFields.type` undefaulted for the update schema; the reason is recorded in a comment there so it is not reintroduced. Re-verified: 28/28 runtime checks pass.
- [x] 7.3 Postman collection (`postman/Ecom.postman_collection.json`) updated — see section 8.

## 9. Banner image upload (multipart)

Added after the user asked for banner artwork to be uploaded by the admin rather than pasted in as a hosted URL.

- [x] 9.1 In `banner.route.ts`, added `multerUpload.fields([{name:"image",maxCount:1},{name:"mobileImage",maxCount:1}])` to `POST /` and `PATCH /:id`. `.fields()` rather than the `.array()` `POST /products` uses, because Banner has two distinct single-file fields rather than one homogeneous list.
- [x] 9.2 In `banner.controller.ts`, added a `mergeUploadedBannerImages` middleware that uploads each attached file via the existing `uploadFileToCloudinary` and writes the resulting `secure_url` onto `req.body`, so the zod schema and the entire service layer keep seeing a plain URL payload. Placed **before** `validateRequest` (design.md Decision 8d): the type contract requires `image` for an IMAGE banner, and an uploaded file only becomes a URL after the Cloudinary round-trip, so validating first would reject a valid upload. Because it now runs first, it also unwraps the `data` JSON field itself.
- [x] 9.3 Rejected an empty file field with a 400 before it reaches Cloudinary — it otherwise failed deep inside the SDK and surfaced as an opaque 500. Found while running the Postman collection programmatically: blank-`src` form-data rows produced zero-byte uploads.
- [x] 9.4 Verified end-to-end against the running server, 19/19 checks: IMAGE banner created from two uploaded files (both stored as distinct real `res.cloudinary.com` URLs); DYNAMIC banner via multipart with no file at all (image stayed null); DYNAMIC + product with an uploaded background; PATCH replacing only the artwork (title/type/other fields preserved — no regression of the 7.2 default-type bug); PATCH with no file leaving the stored image untouched; plain `application/json` with a URL still working; and the type contract still enforced through the multipart path (IMAGE with neither file nor URL → 400, IMAGE carrying a title → 400 even with a file attached, invalid hex → 400). Public listing confirmed to serve the uploaded URL while still resolving the linked product's live price and slug.
- [x] 9.5 Updated the four mutating Postman requests to `formdata` (`data` JSON field + `image`/`mobileImage` file rows with blank `src` for the user to pick), matching the existing `Admin - Create Product (multipart)` convention. Re-ran all 10 banner requests programmatically with real files attached: 10/10 2xx, artwork confirmed stored as Cloudinary URLs. All test banners deleted afterward (`Banner` table back to 0 rows).
- [x] 9.6 Note on flakiness observed during verification: two runs saw `Failed to upload file to Cloudinary` 500s that were **not** caused by this code — the stack showed a TLS socket close from the Cloudinary SDK, `cloudinary.api.ping()` reported the account healthy (498/500 rate limit remaining), a direct upload through the exact same helper path succeeded, and an immediate retry of the identical requests passed. Transient network failure, recorded here so it is not mistaken for a defect later.
