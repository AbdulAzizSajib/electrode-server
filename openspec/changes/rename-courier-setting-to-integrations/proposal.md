## Why

**UI → Courier Setting** is named after one integration but is the only place in the admin where an
integration is configured at all. It answers exactly one question — *which courier receives dispatched
orders* — and it answers it with a radio list, because every credential that makes a courier actually
work lives in the server environment. A merchant who buys this panel cannot connect their own Steadfast
account without a developer editing `.env` and redeploying, and the Facebook Pixel they are already
paying for is configurable only per landing page, never shop-wide.

Renaming the page to **Integrations** is the visible half of the change. The half that matters is that
"Integrations" has to be true: a page called Integrations that still cannot connect anything is a worse
lie than the honest narrow name it replaces. So this change moves courier credentials and webhook
secrets out of the environment into merchant-editable, encrypted storage, and gives Facebook Pixel and
Conversions API a shop-wide home.

This is a panel sold to many merchants. That is the whole argument for the credential move: an
environment variable is a value only a developer can set, so every new merchant would need a `.env` edit
and a redeploy before they could dispatch a single parcel. A second courier is deliberately **not** in
this change — Pathao is a real want, but writing an adapter against documentation with no account to
test it against produces code nobody can trust. It follows when the first merchant asks and an account
exists to verify against.

## What Changes

**Rename and route**

- Sidebar label and page title `Courier Setting` → `Integrations`; page description becomes
  "Manage courier and third-party integrations."
- **BREAKING** Route `/ui/courier-settings` → `/ui/integrations`. The old path is kept as a permanent
  redirect so existing bookmarks and the in-app link from the Courier report page do not 404.
- The page becomes a list of integration cards, each with its own enable toggle and its own Save
  button, rather than a single settings block with one Save bar. Each card saves independently.

**Courier credentials move from environment to database**

- **BREAKING** Two new tables: `Integration` (one row per integration — its enabled state and the
  unguessable `publicId` its webhook URL carries) and `IntegrationCredential` (one row per secret it
  holds), encrypted at rest with AES-256-GCM under a new required `INTEGRATION_ENCRYPTION_KEY` env var.
  `STEADFAST_API_KEY`, `STEADFAST_SECRET_KEY` and `STEADFAST_WEBHOOK_TOKEN` are read from the database
  instead, with a one-time migration that imports whatever is currently in the environment so a running
  shop does not stop dispatching mid-deploy. The env vars are then read-only fallbacks and are removed
  in a later change.
- **BREAKING** `ICourierProvider.isConfigured()`, `isWebhookConfigured()` and `webhookToken()` become
  async, and `createConsignments` / `getStatus` / `getBalance` / `createReturnRequest` receive resolved
  credentials as an argument instead of reading module-level env. Adapters stop being stateless
  singletons over `envVars`.
- New admin endpoints `GET /integrations`, `PUT /integrations/:provider/credentials` and
  `PUT /integrations/:provider/webhook`. Secrets are **write-only**: reads return presence booleans and
  a masked hint, never a value. These are separate endpoints, not `PATCH /settings`, because
  `GET /settings` is public and this change must not put a secret on a row that a public endpoint
  selects from.
- Webhook secrets are **generated by the server**, not typed by the merchant, and the per-provider
  callback URL (`/api/v1/webhooks/<provider>/<publicId>`) is displayed for copying into the courier's
  own panel. The existing `/courier/webhook/:provider` route keeps working; the new path is an alias
  carrying an unguessable id so the endpoint is not enumerable.

**Facebook Pixel and Conversions API**

- New shop-wide `facebookPixel` and `facebookCapi` configuration. The Pixel id is public and lives on
  `StoreSetting.integrationConfig`, served by `GET /settings/public` so the storefront can render the
  pixel. The CAPI access token is a secret and lives in `IntegrationCredential` alongside the courier
  keys — the two halves of one feature are stored differently because only one of them is safe to
  publish.
- Storefront fires shop-wide `PageView` and `Purchase` from the `(shop)` layout, reusing the existing
  `FacebookPixel` component. The per-landing-page pixel is unchanged and takes precedence on
  `(landing)` routes so a campaign is not double-counted.
- Server-side CAPI dispatch for `Purchase` on order creation, with a test-mode flag and test event
  code, fired best-effort so a Meta outage never fails an order.
- **Both halves report the same purchase under one shared event id — the order's own id**, so Meta
  collapses the browser event and the server event into one conversion. No new column and no new
  checkout field: the order id is already server-generated, already unique, and already returned to the
  confirmation. Without deduplication the two paths are additive and every sale is counted roughly twice
  — a merchant reading doubled conversions raises ad spend against revenue that does not exist, which
  makes the feature actively worse than not shipping it.

## Capabilities

### New Capabilities

- `integrations`: One admin surface for connecting third-party services to the shop — what an
  integration is, how its credentials are stored and revealed, how a merchant enables and disables one,
  and the rules every integration card obeys regardless of which service it fronts.
- `courier-credentials`: Merchant-supplied courier credentials and webhook secrets — where they live,
  how they are encrypted, who may read them, how a courier resolves them at dispatch time, and what
  happens when they are missing or wrong.
- `facebook-tracking`: Shop-wide Meta Pixel and Conversions API — which events fire, from where, how the
  two paths are deduplicated into one conversion, precedence against the existing per-landing-page
  pixel, and the rule that measurement failure never becomes an order failure.

## Impact

**Schema / data**

- New `Integration` model (`provider` as PK, `enabled`, `publicId`, timestamps) and new
  `IntegrationCredential` model (`provider`, `kind`, encrypted `value`, `lastFour`, timestamps, unique
  on `(provider, kind)`, cascading from `Integration`), plus a new `StoreSetting.integrationConfig` Json
  column. No enum change — the courier roster is unchanged.
- Migration must preserve the three `pg_trgm` trigram indexes — the generated SQL will contain
  `DROP INDEX` lines for them that have to be deleted, and the standing NOTE block carried forward.
- Data migration importing existing env credentials into the new table.

**Server**

- `src/app/module/courier/` — `courier.provider.ts` (async credential contract),
  `steadfast.provider.ts`, `steadfast.client.ts`, `manual.provider.ts`, `courier.guard.ts` (webhook
  token now resolved async, per provider), `courier.service.ts` (credential resolution threaded
  through; orchestration unchanged).
- New `src/app/module/integration/` module (route/controller/service/validation/interface) and
  `src/app/lib/crypto.ts` for envelope encryption.
- `src/app/module/store-setting/` — `integrationConfig` on the schema, validation and the public
  projection.
- `src/app/config/env.ts` — new required `INTEGRATION_ENCRYPTION_KEY`; Steadfast vars demoted to
  fallback.
- New verify scripts; existing `verify-courier-*.ts` updated for the async provider contract.

**Admin**

- `src/features/ui/courier-settings/` → `src/features/ui/integrations/`, split into one component per
  integration card.
- `src/routes/nav-config.ts` and `src/routes/app-router.tsx` (both, per the two-places rule), plus the
  `/ui/courier-settings` link in `src/features/sales/courier/courier-page.tsx`.
- New `src/lib/api/integrations.ts` and query keys.

**Storefront**

- `(shop)` layout renders the shop-wide pixel; `src/types/store-settings.ts` and
  `FALLBACK_SETTINGS` gain the new public pixel field; order-confirmation fires `Purchase` carrying the
  order's id as the event id. No checkout change — the confirmation already has the order id.

**Deferred**

- A second courier (Pathao). The provider contract is the thing that makes it a self-contained follow-up:
  one adapter file plus one registry entry, with `courier.service.ts` untouched. Nothing in this change
  forecloses it, and the async credential contract landed here is what it will build on.

**Operational**

- `INTEGRATION_ENCRYPTION_KEY` must be set before deploy or the server refuses to boot. Losing it makes
  every stored credential unreadable and every integration must be re-entered.
- Merchants may paste the new callback URL into Steadfast's panel, but are not required to — the
  previously configured webhook URL and its imported token keep working.
