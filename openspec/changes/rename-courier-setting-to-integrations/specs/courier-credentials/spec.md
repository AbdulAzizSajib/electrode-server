## Purpose

Covers merchant-supplied courier credentials and webhook secrets: where they are stored, who may read
them back, how a courier resolves them at dispatch time, and what the system does when they are absent
or rejected. It exists so a merchant can connect their own courier account without a developer editing
the server environment, and so that doing so cannot leak a secret through the shop's public endpoints.

## ADDED Requirements

### Requirement: Courier credentials are stored by the shop, not the environment

The system SHALL store each courier's credentials and webhook secret as shop data that an authorised
admin can enter and replace through the admin panel. Credentials MUST be encrypted at rest and MUST NOT
be readable from any database backup or log without the configured encryption key.

#### Scenario: Merchant enters credentials

- **WHEN** an OWNER or ADMIN submits credentials for a courier
- **THEN** the credentials are stored encrypted, and the courier immediately reports itself as configured

#### Scenario: Credentials are replaced

- **WHEN** an OWNER or ADMIN submits a new value for a credential that already has one
- **THEN** the new value replaces the old one and the old value is not recoverable through the API

#### Scenario: Encryption key is not configured

- **WHEN** the server starts without its credential encryption key configured
- **THEN** the server refuses to start rather than storing or reading credentials unencrypted

#### Scenario: Encryption key does not match stored data

- **WHEN** a stored credential cannot be decrypted with the configured key
- **THEN** the courier reports itself as unconfigured, the failure is logged once, and no dispatch is attempted with an empty credential

#### Scenario: Existing environment credentials keep working through the transition

- **WHEN** a shop that had courier credentials in the server environment is upgraded
- **THEN** those credentials are carried into encrypted storage and dispatch continues without the merchant re-entering anything

### Requirement: Stored secrets are never returned

Reading a courier's configuration SHALL disclose only whether each secret is present, and at most a
masked hint that cannot be used to reconstruct the value. No endpoint, response envelope, log line, or
error message MAY contain a stored credential or webhook secret.

#### Scenario: Admin reads the integration listing

- **WHEN** an OWNER or ADMIN requests the integrations listing
- **THEN** each credential is reported as present or absent, with no credential value in the response

#### Scenario: Public store settings are requested

- **WHEN** the public store settings endpoint is requested
- **THEN** the response contains no courier credential, no webhook secret, and no field from which either could be derived

#### Scenario: A courier call fails with an authentication error

- **WHEN** a courier rejects a request because the credentials are wrong
- **THEN** the error surfaced to the admin says the credentials were rejected without echoing any submitted or stored value

### Requirement: Webhook secrets are generated by the server

The system SHALL generate each courier's webhook secret itself rather than accepting one chosen by the
merchant, and SHALL present the corresponding callback URL for the merchant to copy into the courier's
own panel. Each courier's webhook endpoint MUST accept only that courier's secret.

#### Scenario: Merchant generates a webhook secret

- **WHEN** an OWNER or ADMIN requests a webhook secret for a courier
- **THEN** the server generates an unguessable secret, stores it encrypted, and displays it once together with the callback URL for that courier

#### Scenario: Regenerating invalidates the previous secret

- **WHEN** a merchant generates a new webhook secret for a courier that already had one
- **THEN** the previous secret is no longer accepted, and the card warns that the courier's panel must be updated

#### Scenario: Webhook presented with another courier's secret

- **WHEN** a webhook for courier A arrives carrying courier B's secret
- **THEN** the request is rejected and no shipment status is changed

#### Scenario: Webhook arrives while no secret is configured

- **WHEN** a webhook arrives for a courier that has no webhook secret stored
- **THEN** the request is rejected rather than accepted unauthenticated, and the rejection is logged

#### Scenario: Previously configured callback URL keeps working

- **WHEN** a courier posts to the callback URL configured before this change
- **THEN** the notification is still accepted, authenticated against that courier's stored secret

### Requirement: A courier resolves its own credentials at call time

Each courier integration SHALL obtain its credentials when it makes a call, so that a credential changed
in the admin takes effect without restarting or redeploying the server. Routing of an existing
consignment SHALL continue to follow the courier that created it, regardless of which courier is
currently selected or which credentials have since changed.

#### Scenario: Credentials changed between dispatches

- **WHEN** a merchant replaces a courier's credentials and then dispatches orders
- **THEN** the dispatch uses the new credentials with no restart

#### Scenario: Status is read for a consignment created by a different courier

- **WHEN** the system reads the status of a consignment created by a courier other than the currently selected one
- **THEN** it uses that consignment's own courier and that courier's credentials

#### Scenario: Dispatch attempted with credentials missing

- **WHEN** a dispatch is requested for a courier whose credentials are absent
- **THEN** the dispatch is refused before any order is sent, and the refusal names the missing configuration

#### Scenario: Switching couriers with parcels in flight

- **WHEN** a merchant tries to switch couriers while consignments created by the current courier are still in transit
- **THEN** the switch is refused and the refusal states how many consignments are still in flight

### Requirement: Moving credentials out of the environment changes no dispatch behaviour

Changing where credentials are stored SHALL NOT change how orders are dispatched, how results are
matched back to orders, how batches are persisted, or how a courier's reported status is applied. The
existing guarantees MUST continue to hold unchanged.

#### Scenario: Dispatch results are matched by invoice

- **WHEN** a batch of consignments is created
- **THEN** each result is matched back to its order by invoice rather than by position in the response

#### Scenario: A batch is persisted before the next is sent

- **WHEN** a dispatch spans more than one batch
- **THEN** each batch's results are persisted before the following batch is sent

#### Scenario: A courier call times out

- **WHEN** a dispatch call times out or returns an unreadable response
- **THEN** the outcome is recorded as unconfirmed rather than failed, and no automatic retry is offered for it

#### Scenario: The same status arrives by two routes

- **WHEN** a status is reported by webhook and the same status is later discovered by polling
- **THEN** both are interpreted identically and the shipment is not double-applied
